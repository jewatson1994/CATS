# Backend performance implementation and acceptance report

Branch: `feature/backend-performance-refactor`. No commit or push. Existing unrelated working-tree changes remain. This report maps the attachment's 50 requested report items. **The comprehensive performance objective is not yet proven complete.** The recorded 100k simplified request still takes 6.91 seconds; filtered fallback and remaining header/dependency costs still need measurement. No real PostgreSQL or disconnected-VM acceptance was performed.

Evidence: [inventory](backend-performance-inventory.md), [baseline](backend-performance-baseline.json), [after](backend-performance-after.json), [query plans](backend-performance-query-plans.md), and current source/tests. The JSON measurements capture the latest measured working-tree checkpoint. Their source hashes identify the measured source. Final integrated tests passed; disconnected acceptance remains outstanding.

1. **Branch created:** Current branch is `feature/backend-performance-refactor`; inherited functionality and dirty files were preserved.
2. **Baseline methodology:** Direct actual route invocation includes DTO/JSON serialization, cProfile and tracemalloc. Fresh ORM sessions, SQLite, ten services, three scans each, one observation per finding; half the findings belong to the target service. Authentication, middleware, HTTP transport, database-internal rows examined, and Python rows considered are not measured. Single observations are not p95 or throughput results; OS caches may be warm.
3. **Endpoints audited:** Inventory covers both dashboards, service list/detail, raw/simplified findings, activity, history, artifacts, exports, remediation and validators. Dedicated loaders were also inspected for dependencies, ingestion and watchlist refresh. This is a source audit, not runtime coverage of every endpoint.
4. **Worst bottlenecks:** Broad service graphs before tab dispatch; findings header preparation scaling with all findings; simplified grouping and evidence hydration; historical artifact files; global audit loads; repeated configuration lookup. The 100k simplified baseline failed with SQLite variable limits.
5. **Full-table loads removed:** Audit matching now occurs before limiting/hydration; artifact loaders select latest revisions and validation metadata; dashboard row hydration is paged. Full-service exports and remaining scalar preparation still require further work.
6. **Python filtering removed:** Raw filters and selected dashboard/remediation predicates run in SQL. Compatibility-sensitive Unicode matching and some portfolio/service filters remain in Python; this requirement is partial.
7. **Python sorting removed:** Raw pages and mixed exception pages sort before SQL pagination. Lightweight dashboard ID ordering preserves existing semantics. Export retains exact Python `name.lower()` ordering over ID/name projections.
8. **N+1 queries removed:** Snapshot configuration resolves once per 50-service batch, observations/header relations load in bulk, activity actors load in bulk, and watchlist settings load once per refresh. Validator listing was already free of the suspected per-validator attempt lookup.
9. **Giant ORM graphs removed:** Purpose-specific projections and page-only hydration replace broad list graphs. Artifact latest-revision loading and independent service tabs reduce history materialization. Whole-service export remains a bounded improvement area.
10. **Dashboard architecture:** Finding and policy metrics use SQL aggregates; durable execution summaries avoid repeatedly parsing latest evidence. Paged service rows hydrate only selected services. Some portfolio computation/selectors still scale with authorized service count.
11. **Service detail architecture:** Dispatch differentiates activity, dependencies, artifacts, remediation, POAM, architecture and validation paths. Architecture/validation and isolated activity/POAM paths have header-only queries; dependency preparation and other header paths still require final verification. Dependency headers still prepare the full current finding state.
12. **Findings endpoint architecture:** Raw pages combine filtered IDs then hydrate selected records; SQL header aggregates avoid per-finding materialization. The default active simplified path with all/vulnerability type and no search/resource/severity filters uses SQL eligibility/compliance plus a bounded header, scalar member/group keys and page-only support. Filtered and other-state requests retain the compatibility fallback; their large-data latency is unmeasured. Member collection/grouping still scales with eligible findings.
13. **Pagination implementation:** SQL LIMIT/OFFSET for raw findings, dashboard selected IDs, dependency rows and remediation. Activity is SQL-scoped and bounded to 500 records, but is not paginated. Global exceptions now UNION vulnerability/configuration/pending IDs into one ordered page; high page numbers clamp before fetch. Some large collections and full-export contracts remain unbounded.
14. **Filtering implementation:** Authorization scope, active/resolved/exception state, severity, identifiers, dates and supported text/resource filters apply before raw pagination. Pending exception filters retain their previous route semantics; no claim of new unsupported filters.
15. **Sorting implementation:** Stable raw ordering and mixed exception `created_at DESC, record_type, record_id` prevent overlaps/skips. Existing portfolio ordering semantics are preserved. Deep OFFSET costs are not eliminated.
16. **Search implementation:** Raw search uses SQL expressions, bounded observation candidates and dialect-specific compatibility paths. Unicode/casefold and literal wildcard behavior have regression coverage; PostgreSQL execution remains unverified.
17. **Authorization/query integration:** `None` means unrestricted and a set restricts IDs; empty export scope denies. Export checks `service.export`, views check `service.view`; permission restrictions precede evidence hydration and counts. Mixed-page tests exclude unauthorized records.
18. **KEV/EPSS optimization:** Shared risk predicates use bulk catalog/configuration inputs rather than a database query per finding. Mutable intelligence is not frozen into immutable scan summaries. Catalog refresh and multi-process behavior need deployment acceptance.
19. **Policy evaluation optimization:** SQL compliance predicates replace raw header scans where supported; deterministic global/group policy precedence remains. The default simplified route moves risk eligibility/compliance to SQL; scalar grouping remains in Python, and filtered fallbacks still use canonical Python evaluation.
20. **JSON/evidence parsing:** Execution summaries store bounded evidence-derived fields; summary reads fetch payloads only for missing/stale summaries in batches of 32. Latest artifact files are selected separately from revision history. Full retained evidence remains authoritative.
21. **Materialized state added:** `ExecutionSummary`/`execution_summaries` plus execution `payload_digest`; versioned data stores normalized evidence fields and severity counts. Also added disposable `dependency_projections` and `dependency_projection_rows` for SQL dependency filtering/paging. These are not universal materialized service policy tables.
22. **Invalidation rules:** ORM flush hooks regenerate execution summaries when payload/complete/digest changes. Readers check digest, summary version and completeness, using a non-writing legacy fallback. Direct SQL payload writers must update/clear digest in the same transaction; nested in-place JSON mutations need disciplined writers. Current policy/intelligence stays evaluated independently. Dependency fingerprints include projection version, payload digest (legacy payload hash), ordered observation package/version/image/fix/evidence fields, finding CVE/severity, current risk answers and sorted watchlist matches. Rebuilds use an owned isolated-engine cache transaction where possible. Explicit Connection bindings, shared SQLite pools and active SQLite writers use the caller transaction without committing it; request rollback discards that disposable cache. Warm historical payloads are deferred; current header work remains service-sized. Service deletion explicitly purges derived cache tables.
23. **Indexes and rationale:** Existing service/active, episode/name/order, observation/finding/execution, execution/scanned, POAM/status/due and active-exception indexes support scoped filters and latest joins. Startup preserves idempotent creation. Do not attribute all listed indexes to this refactor or claim every plan selects a composite index.
24. **Query-plan findings:** Actual SQLite raw-page plans show indexed finding/exception lookups, UNION evaluation and a temporary B-tree for ordering. They cover a 1k raw active fixture, not dashboards/simplified. PostgreSQL SQL compiles; real EXPLAIN is absent.
25. **Ingestion/write-side:** Watchlist refresh walks retained execution evidence in batches of 32 without committing partial work; image reconciliation uses EXISTS instead of observation-history hydration. Summary hooks share the write transaction. Full ingest/upsert throughput and lock contention were not benchmarked.
26. **Exports:** Service snapshot authorizes projected IDs first, bulk-resolves configuration, and uses disposable identity maps for batches of 50. Exact XLSX cells/header/format/order remain. Workbook output remains in memory: this is **not true streaming**. Whole-service activity is SQL-scoped; whole evidence exports still need size/memory acceptance.
27. **Remediation:** Independent scoped POAM/remediation loaders and combined mixed exception pagination reduce broad graph work. Tests cover mixed timestamp ties, global page boundaries, permissions, pending state and clamping. No decision/lineage removal was intended.
28. **Helm:** Artifact workspace loads current revisions/runs instead of every revision file graph. Recursive discovery/scanner behavior is preserved; scanner/network parsing/provisioning speed was not measured or claimed improved.
29. **Managed validators:** Audit confirmed listing already avoids attempt N+1, detail attempts remain bounded. Provisioning/readiness/status payload inspection remains a potential blocking cost; no new validator cache or measured speedup is claimed.
30. **API payload reductions:** Raw response sizes stay approximately 12KB and page-only objects are loaded. Recorded simplified payload remains large at approximately 876KB because group members remain large. Dashboard payloads grow slightly with metadata. Uniform bounded payload targets are not yet achieved.
31. **Frontend API changes:** Pagination metadata/context changes are adapted through frontend projections. This is backend performance work; inherited React changes must not be attributed wholesale to it. Verify service tab/POAM/remediation pagination in the final integrated frontend.
32. **Diagnostics:** `CATS_PERFORMANCE_DIAGNOSTICS` enables lightweight request/query/object/stage measurements without SQL parameters, identities or full URLs in logs. Benchmark harness additionally measures actual DBAPI fetched rows and traced Python peak memory. DBAPI rowcount is explicitly not fetched SELECT rows.
33. **Schema changes:** Added durable execution summary model/table and nullable payload digest; summary rows are keyed by execution. Dependency projection tables store fingerprints plus filterable row fields and JSON DTOs keyed by execution/position. No replacement of retained scan evidence.
34. **Migrations:** Startup additive `create_all`/column checks retain legacy SQLite/PostgreSQL compatibility paths. Backfill is lazy and bounded on reads, hooks populate new writes. Idempotence has SQLite regression coverage; production PostgreSQL upgrade/rollback needs testing.
35. **Query-count tests:** Diagnostics, findings, dashboard paging, execution summaries, scoped activity, ingestion, artifact tabs and snapshot export tests assert relevant bounded/bulk patterns. Export verifies three configuration queries for 120 authorized services. These tests do not establish a universal request query budget.
36. **Row-fetch tests:** Raw page bounds, selected dashboard ORM rows, artifact latest-revision loading, history bounds and batch residency have focused coverage. Mixed exceptions return one combined page. Some tests bound ORM objects rather than exact DBAPI fetches; report that distinction.
37. **1k results:** Recorded raw duration 288.9 to 211.2ms, fetched rows 1,232 to 267; simplified 945.0 to 163.1ms, rows 1,731 to 734. Dashboard results are in the table; no broad uniform speedup claim.
38. **10k results:** Recorded raw duration 1,329.2 to 190.9ms, fetched rows 10,232 to 267; simplified 8,894.8 to 758.5ms, rows 17,031 to 7,034. Dashboard results are in the table; no broad uniform speedup claim.
39. **100k results:** Raw 12,475.5 to 273.2ms and 100,232 to 267 rows. Simplified baseline failed after 12,154.9ms (`too many SQL variables`, zero-byte response); latest after succeeds but needs 6,910.1ms, 70,034 fetched rows, 19 queries and 47.448MB (45.2MiB) traced peak Python memory. It still misses responsiveness acceptance; filtered fallback is unmeasured.
40. **Before/after major endpoints:** The complete checkpoint table below covers all four endpoints at each fixture size; benchmark source hashes and instrumentation caveats apply.
41. **Response sizes:** Table reports bytes, including the failed baseline's zero bytes. Equal size is not proof of byte-equivalent behavior; semantic tests are separate. Simplified 100k cannot claim reduction against a failed response.
42. **Backend tests:** Final integrated run: **1,405 passed, 1 skipped, 7 warnings in 145.77 seconds**, covering all final production changes. A cache-purge assertion added to the existing service-deletion test after suite collection passed independently (**1 passed in 1.90 seconds**), confirming dependency projections/rows and execution summaries are removed. Focused mixed-page, snapshot bounds and permission-residency checks also pass. `git diff --check` passes. These results do not replace deployment acceptance.
43. **Frontend tests:** Final frontend run: **163 tests passed across 28 files**.
44. **TypeScript:** Fresh type check passed.
45. **Production build:** Fresh frontend production build passed; disconnected payload/VM build acceptance has not occurred.
46. **PostgreSQL:** Dialect compilation tests cover representative raw statements and dashboard ordering; portable JSON/ordering branches preserve compatibility intent. No server execution, real EXPLAIN, upgrade, concurrency or performance evidence exists.
47. **SQLite:** Actual benchmarks and raw EXPLAIN available. Large IN parameter lists previously failed at 100k; batching avoids that specific failure. SQLite UDF/dialect paths preserve casefold behavior. Locking/concurrent ingest acceptance remains outstanding.
48. **Remaining bottlenecks:** Recorded simplified 100k grouping/headers; service-sized scalar preparation on some tabs; authorized service selectors/portfolio work; large evidence and group payloads; whole-service exports/in-memory workbook; deep offsets; mutable intelligence refresh and dependency-cache invalidation; validator blocking inspection. Default simplified improvements are reflected in the latest checkpoint; filtered fallback, dependency/current-header costs and broader endpoints still require measurement before claiming closure.
49. **Compatibility changes:** Stable mixed exception ordering now produces one correct page rather than up to three independently paged lists; out-of-range exception pages clamp before fetch. Snapshot output contract retained. Latest-only artifact projections require verifying history navigation. No removed scanner/remediation/offline feature is intended; acceptance remains incomplete.
