# SUSE, Microsoft, and Chainguard source review

Reviewed 2026-10-19 for redistribution in the offline intelligence bundle. Public accessibility, a software repository's license, and permission to redistribute the actual security data are separate checks. Only SUSE is included by `scripts/embedded_vendors.py`. Acquisition inputs and review samples stay in the external temporary cache.

## SUSE: included

SUSE explicitly licenses its CSAF advisory and CVE-indexed VEX **data** under CC-BY-4.0 on its [CSAF documentation page](https://www.suse.com/support/security/csaf/). Each included VEX document independently carries the same data-license notice and identifies SUSE as its vendor publisher. The adapter requires that exact notice and publisher namespace; a changed notice fails closed. The release copies the complete [CC-BY-4.0 legal text](https://creativecommons.org/licenses/by/4.0/legalcode.txt) as `LICENSE-suse.txt`, attributes SUSE Product Security Team, and retains the original object and source URL. The reviewed legal-text SHA-256 is `9ba9550ad48438d0836ddab3da480b3b69ffa0aac7b7878b5a0039e7ab429411`. JSON formatting changes, but publisher statements, product trees, references, notices, and revision history are preserved.

The public [VEX directory](https://ftp.suse.com/pub/projects/security/csaf-vex/) supplies `index.txt`, `changes.csv`, year directory listings, and individual JSON documents. These HTTPS downloads succeeded without authentication. No archive or numeric request quota was found on the reviewed publisher pages. The builder uses four concurrent downloads, never infers unlimited service capacity, and pins every response's URL, hash, byte count, and acquisition time. Selection intersects both publisher indexes with directory listings because some recently indexed paths returned HTTP 404. Replaying the lock does not refresh these indexes.

The measured input inventory contains **71,607 indexed paths**, **71,711 directory-listed documents**, and **71,592 eligible indexed documents**. Fifteen indexed paths were absent from the directory listings. The selected **2,048 documents occupy 948,130,582 original bytes**; 69,544 eligible documents remain outside this cohort. A linear estimate at the selected cohort's mean is about **33.1 GB** for the entire eligible corpus; this is an extrapolation, not a measured complete download. This run expanded an initial 512-document cohort to 2,048. No SUSE statements are selected individually or truncated to fit.

The default cap is 2,048 documents, configurable up to 10,000 through `prepare_vendor_sources(max_documents=...)`. Documents sort by descending publisher change timestamp and path. Acquisition stops at a 2 GiB cohort bound after a bounded batch; indices/documents have 32 MiB parsing bounds and output documents a 1 MiB canonical JSON bound. The shared CSAF parser additionally enforces its product/statement/depth limits. Oversized, malformed, duplicate-key, or unreviewed-license documents are excluded with explicit counters. These are technical coverage limits, not license restrictions.

SUSE `known_affected`, `known_not_affected`, `fixed`, and `under_investigation` retain their original CSAF meaning. `recommended` remains a separate supplemental advisory, never a `fixed` assertion. Recommendations carry exact `affected_identities` and the original document. A component's PURL, qualifiers, version, and containing product CPE/PURL are retained. A relationship assertion requires exact `csaf_product_context`; a matching bare package PURL is insufficient. No source/binary-package, distro, architecture, or name-to-PURL equivalence is invented. Versionless publisher identities stay preserved but cannot establish version-specific runtime matches.

For example, [CVE-2015-4588](https://ftp.suse.com/pub/projects/security/csaf-vex/2023/cve-2015-4588.json) supplies `pkg:rpm/suse/libwmf@0_2-7?upstream=libwmf-0:0_2-7.src.rpm` with `known_not_affected` in `cpe:/o:suse:sled:15:sp3`. Tests use a clearly marked excerpt of this real assertion: the exact identity/context matches; missing or different product context, version, or qualifier does not. These publisher identifiers are preserved even when their version spelling is unusual.

Offline validation verified every locked input hash and reproduced the exact emitted-record digest `ed3b4eaa587e1ac135fe8332f0d9f7cd1ffae695a4e9ca3ee88b4c254b23c839`.

## Microsoft MSRC: deferred, no records bundled

Microsoft's [official API repository](https://github.com/microsoft/MSRC-Microsoft-Security-Updates-API) contains getting-started code and documentation for its CVRF API. Its software license does not establish a license for the API's security data. Anonymous requests to the [v3 update index](https://api.msrc.microsoft.com/cvrf/v3.0/updates) and [October 2026 CVRF JSON](https://api.msrc.microsoft.com/cvrf/v3.0/cvrf/2026-Oct) succeeded: the index had 193 update entries, and the monthly sample contained 2,135 vulnerability entries in 26,836,762 bytes. These are research measurements; none are release inputs. The CVRF route supplies a complete monthly document; CSAF discovery below uses an index and individual documents. A single all-history bulk archive was not established. No numeric quota was established from the reviewed official API material.

Microsoft also publishes actual CSAF VEX, initially for Azure Linux, as explained in its [VEX announcement](https://www.microsoft.com/en-us/msrc/blog/2025/10/toward-greater-transparency-machine-readable-vulnerability-exploitability-xchange-for-azure-linux). The [provider metadata](https://msrc.microsoft.com/csaf/provider-metadata.json) advertises advisory and VEX directories and explicitly sets `mirror_on_CSAF_aggregators` to `false`. Its [VEX index](https://msrc.microsoft.com/csaf/vex/index.txt) contained 19,429 paths. A sampled [CVE-2026-109351 document](https://msrc.microsoft.com/csaf/vex/2026/msrc_cve-2026-109351.json) was 5,276 bytes; it declared public/TLP WHITE distribution and a warranty disclaimer, but no redistribution license. Its product tree used publisher-local numeric IDs and names, without PURL helpers for the examined packages.

Two blockers are distinct: **data redistribution permission has not been established for this bundle**, and **a reviewed exact product mapping adapter is not implemented**. Microsoft's [general terms](https://www.microsoft.com/en-us/legal/terms-of-use) impose copying/distribution and document-use limits unless another license applies. The sampled disclaimer, TLP label, public API, and code license do not supply that missing permission. This review does not claim Microsoft forbids every form of downstream security analysis, or that its aggregator flag is a universal redistribution prohibition. A feed-specific grant and product identity specification would allow reassessment; copying numeric product IDs into invented PURLs would not.

## Chainguard/Wolfi: conditional data licenses; no records bundled

The [official scanner integration documentation](https://github.com/chainguard-dev/vulnerability-scanner-support/blob/main/docs/foundational_concepts.md) explicitly applies CC-BY-NC-ND-4.0 or Chainguard's commercial-scanner license to **OSV and both SecDB data feeds**. The Apache licenses of Wolfi/software tooling do not override these data terms. Current OSV v3 uses one advisory per file with an [index](https://advisories.cgr.dev/chainguard/v3/osv/all.json); v2 groups by upstream alias. The feed includes Wolfi and enterprise packages, with package/component and architecture details. The legacy SecDB endpoints are `https://packages.wolfi.dev/os/security.json` and `https://packages.cgr.dev/chainguard/security.json`; new integrations are directed to OSV. Authentication requirements for the current feeds were not tested; feed-count and quota measurements were not made, and no advisory-data bulk download was performed. These access questions remain unverified, separate from the documented license-scope blocker below.

The [Wolfi advisory repository](https://github.com/wolfi-dev/advisories) was archived January 7, 2026 and directs current consumers to the security site. Its [data LICENSE](https://github.com/wolfi-dev/advisories/blob/main/LICENSE) contains commercial-scanner restrictions on modification and redistribution as part of other offerings. Separately, the [current commercial-scanner terms](https://www.chainguard.dev/legal/chainguard-license-for-commercial-scanners), updated September 1, 2026, use a non-sublicensable grant, competitor/competitive-offering restrictions, and required notices for permitted sharing. These two texts differ; the archived text is not presented as the current web license.

The noncommercial/no-derivatives route and the conditional commercial-scanner route do not establish unrestricted redistribution rights for the proposed general-purpose bundle and its recipients. Eligibility and applicable downstream rights have not been established. This is a concrete license-scope blocker, not an assertion that the vendor provides no feed. The old archive also cannot represent current coverage. A compatible written permission or a verified eligible distribution model, followed by exact OSV component/architecture mapping work, is needed before inclusion. Included counts are 0 for both Microsoft and Chainguard/Wolfi; 0 does not describe their published corpus sizes.

### Separate current Chainguard Libraries VEX

Chainguard does publish current vendor VEX. Its [Libraries foundational guide](https://github.com/chainguard-dev/vulnerability-scanner-support/blob/main/libraries/foundational_concepts.md) explicitly distinguishes Libraries OpenVEX from the Images/Wolfi OSV and SecDB feeds above. The [remediation documentation](https://edu.chainguard.dev/chainguard/libraries/policies-and-security/cve-remediation/) links a public [VEX index](https://libraries.cgr.dev/openvex/v1/all.json); the [scanner implementation guide](https://github.com/chainguard-dev/vulnerability-scanner-support/blob/main/libraries/scanning_implementation.md) also documents `index.json` and individual package files under `https://libraries.cgr.dev/openvex/v1/`. This establishes indexed retrieval; no single complete VEX archive or numeric request quota was established in this review.

On 2026-10-20, bounded anonymous HTTPS reads succeeded for `all.json` (96,245 bytes) and the documented [urllib3 package file](https://libraries.cgr.dev/openvex/v1/pypi/urllib3.openvex.json) (4,535 bytes). The latter is OpenVEX 0.2.0, identifies the Chainguard Team as author and Chainguard as supplier, and contains six `fixed` statements with CVE aliases and exact remediated PURLs, including `pkg:pypi/urllib3@1.26.14%2Bcgr.2`. These are research observations, not release inputs or full-feed measurements. The [chainctl reference](https://edu.chainguard.dev/platform/chainctl/chainctl-docs/chainctl_libraries_remediate/) independently states that the published VEX feed needs no credentials.

The Libraries integration guide requires preserving complete remediated versions, including Python `+cgr.N` and Java `-0.cgr.N` suffixes, and distinguishing Chainguard origin. A future adapter must retain exact PURLs, explicit CVE aliases, supplier scope and the vendor's status; it must not apply these statements to an upstream base version or assume a fix is installed because a remediated version exists. Libraries VEX does not establish image-digest or Wolfi APK applicability. A separate current image-scoped or Wolfi-specific VEX publication was not verified by this review.

**VEX-specific redistribution remains incomplete research, separate from the established advisory-license conditions above.** Neither the reviewed Libraries guides nor the sampled OpenVEX document establishes a data grant for redistributing this feed in the CATS image. The repository's Apache software license and the OSV/SecDB licensing statement must not be extended to a separate VEX feed by inference. This is not a finding that VEX redistribution is prohibited. Inclusion requires an explicit feed-specific grant or authoritative confirmation of applicable terms and downstream rights, followed by bounded acquisition and a reviewed package-origin/identity adapter; image-level use additionally requires verified image applicability. No Libraries VEX records are bundled.
