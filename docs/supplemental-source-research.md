# Supplemental intelligence source review

Reviewed 2026-10-20 UTC. These release-time adapters produce independently attributed supplemental records. They do not issue vendor VEX, claim that a CVE affects an installed product, or make HTTP calls when the application runs. Source snapshots, their acquisition dates, SHA-256 hashes, and the reviewed terms accompany the signed release.

OSV transport uses public unauthenticated `https://storage.googleapis.com/osv-vulnerabilities/<ecosystem>/all.zip` downloads. The chosen ecosystem archives also contain GHSA, MAL and other publishers. Those entries are counted as exclusions rather than being incorrectly relicensed as Go/PyPA/RustSec data; GitHub-reviewed GHSA records have a separate package source. Full original OSV objects preserve withdrawal, package ecosystem/name, ranges, fixed versions, aliases and references. No PURL or affected/not-affected assertion is invented from an ecosystem name.

These six supplemental adapters fetch one bulk data object per selected snapshot, plus separately pinned terms files; they do not make per-CVE API requests. NVD's [API](https://nvd.nist.gov/developers/start-here), FIRST's API and OSV's API are available acquisition alternatives, but their authentication/rate-limit behavior is not relied upon by this implementation. GitHub/GCS bulk service throttling or transport errors fail acquisition; replay uses the verified local cache. A refreshed EPSS daily snapshot is needed to retain current risk information, and a changed feed may be stale even when downloaded today.

## RustSec license-file clarification

The acquired RustSec snapshot contains 538 distinct CVE-linked advisories producing 607 records: 523 advisories / 592 records explicitly declare `CC0-1.0`, and 15 advisories / 15 records declare `CC-BY-4.0`. All 15 imported entries also explicitly declare `license = "CC-BY-4.0"` in their official original RustSec files; [RUSTSEC-2026-0007](https://github.com/rustsec/advisory-db/blob/main/crates/bytes/RUSTSEC-2026-0007.md) is one example. A GHSA alias alone does not identify imported content: many CC0 entries also have GHSA aliases. The inclusion basis is the [RustSec repository data-license notice](https://github.com/rustsec/advisory-db/blob/main/LICENSE.txt), each advisory's explicit license declaration, and [GitHub's Advisory Database CC-BY-4.0 terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features#advisory-database). GitHub attribution is provided at [GitHub Advisory Database](https://github.com/advisories), with original references and aliases preserved.

The upstream notice points to [`LICENSES/CC-BY-4.0.txt`](https://github.com/rustsec/advisory-db/blob/main/LICENSES/CC-BY-4.0.txt), but that file actually contains CC-BY-SA-4.0 full text. Its acquired 20,138 bytes have SHA-256 `28a9529c7d0bb4dc51f4bf5c116a3d16ef247a052f7591466768ddf563fd1cf5` and are retained unchanged as `LICENSE-osv-rust-ccby.txt`. This is an upstream notice/full-text inconsistency, not evidence of a redistribution prohibition. The package retains the original notice and conflicting file for provenance, includes correct CC-BY-4.0 full text as `LICENSE-ghsa.txt`, and explains the discrepancy in `ATTRIBUTION.txt`. All 607 records remain included on the explicit declaration basis above; no license is inferred from OSV transport or converter code.

## Debian Security Tracker decision

The [public JSON export](https://security-tracker.debian.org/tracker/data/json) and [source repository](https://salsa.debian.org/security-tracker-team/security-tracker) are technically feasible offline sources. The natural key is Debian source package plus CVE plus distribution release; release status/fixed version must remain attached to that identity. Converting source-package status into a binary-package VEX assertion would require independently verified source/binary mapping. The JSON export is the considered bulk route. No release adapter was implemented, so authentication requirements and numeric request quotas were not validated for a Debian acquisition workflow.

This review found no explicit redistribution license covering the tracker **data**. A [September 2026 request on Debian's own mailing list](https://lists.debian.org/debian-security-tracker/2026/09/msg00023.html) raises this same unresolved distinction between public access and redistribution permission. No permission is inferred from licenses applying to tracker software, the Debian project generally, or OSV's converter. Debian data is therefore excluded pending a clear data-specific grant. This is a terms-evidence gap, not an unavailable parser or an unsupported format. No Debian data is silently substituted through OSV.

## Trust, freshness and bounds

Provider archive acquisition and release signing have separate roles. TLS, pinned input digests and reviewed terms support acquisition provenance; the package signature authenticates the distributed snapshot, not an upstream vendor signature. Terms files are byte-pinned and copied into the release; changed bytes require a new review. FIRST and NIST terms currently use full HTML snapshots, so a presentation-only website change can also require renewing a pin.

EPSS overlays query only the finding CVEs and accept exact record hashes from the authenticated installation. Source disablement, trust removal, future dates, expired score publication dates, malformed probabilities or conflicting scores prevent their use. A newer external EPSS catalog wins. Missing scores stay unknown, including scores removed from a newer package; zero remains a valid score. EPSS probabilities and CISA SSVC `Exploitation: none` never become negative exploitation evidence. Historical advisory data and NVD status remain evidence, not automatic scanner finding changes.

Each download is bounded by the builder's 512 MiB acquisition limit. Archives are read without filesystem extraction, with at most one million members and 2 GiB declared uncompressed content. OSV members are limited to 8 MiB; CISA source CVE documents to 32 MiB before selecting their complete CISA containers; NVD gzip JSON to 512 MiB uncompressed; EPSS lines to 4,096 characters. Final records remain subject to the package's 8 MiB line bound. These are explicit release safety limits, not silent truncation. Unit tests cover scope, aliases, terms changes, archive bounds, score validation, source controls, exact membership and publication freshness.

The offline verification script supports `--already-installed` for a normal application image whose startup has already imported the package. Set `DATABASE_URL` explicitly to the disposable loopback PostgreSQL database, then run `python scripts/verify-embedded-intelligence.py --already-installed --report /tmp/intelligence-report.json`. This skips only the first import; repeat import is still timed. The report computes exact full-database source/category/status counts, unique CVEs, exact CVE–product pairs, parsed package names, and versioned/context-bearing rows. Counts include immutable historical revisions and are not described as current applicability. Distinct source/PURL values are streamed; raw corpus JSON is not fetched for counting. PostgreSQL performs the distinct aggregates and can spill their working sets to disk.

Vendor demonstrations use actual installed, explicitly versioned Ubuntu, Red Hat and SUSE identities. Each reports current-time freshness separately from a diagnostic evaluated at its actual document publication time, with contradictory distribution or CSAF containing-product controls and a wrong-PURL control. Neither source trust nor age limits are changed. EPSS and KEV demonstrate actual signed membership, unknown controls, publication/acquisition times and lookup durations. PostgreSQL reports include actual table/index sizes and an estimated query plan, clearly distinguished from measured counts and timings. The small helper fixtures test the report calculations only; they are not acceptance evidence or shipped intelligence.


Runtime enrichment membership is materialized in two append-only tables: small per-install catalog metadata and exact catalog-to-record membership. They are populated in the same transaction as authenticated package import; deduplicated records can belong to multiple installations, and removed records remain historical without becoming current matches. Database triggers reject updates/deletes to this projection. Existing installations are materialized once when their matching signed package is verified at startup. Subsequent unchanged installs project only the stored sequence, version and signed-manifest digest. Assessment overlays read small catalog metadata and join membership for requested CVEs, avoiding full EPSS hash-set construction, manifest decoding and historical score transfer. These additive tables use the existing startup `Base.metadata.create_all` registration. Startup remains synchronous with respect to readiness; an import failure is recorded and permits startup to continue.

The acceptance coverage report also counts currently fresh, versioned identity rows by source and status at one explicit `freshness_as_of`. It checks source enabled/trusted/authority settings, current TLS host or signature-key verification, original document issuance and expiry, and withdrawal. Required CSAF and distro context rows are counted separately. These retained-row counts deliberately do not claim unique resolved applicability, latest-revision resolution, observed context availability, or absence of conflicts. Document metadata streams in bounded batches and statement counts remain SQL aggregates.
