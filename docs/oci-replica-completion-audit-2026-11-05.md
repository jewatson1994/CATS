## Final architecture

1. **System A:** The existing service/distribution review freezes Service Export records, assessment decisions, documentation and complete BOE. Cyber approval reserves authoritative identity/sequence. The durable publication worker copies exact image/chart graphs, signs them and the release/evidence, then publishes the discovery reference only after verification.
2. **OCI:** The release artifact contains the signed document, detached signatures, public-key material and evidence layers. The document names every artifact and its immutable signature manifest. Harbor must replicate the complete service subtree, including charts, child manifests, layers, signatures and the release repository. Embedded public keys are checked against independently configured fingerprints.
3. **System B:** Background synchronization reads only the configured local registry, verifies the complete graph and bounded archive, and enters one transaction for identity mapping, frozen relational reconstruction, history and active sequence. Failed or older candidates cannot replace active state. Retained evidence is sealed and verified; normal users cannot edit it.
4. **Proxy:** Machine authentication and local service authorization precede exact repository/digest graph checks. Valid active releases authorize normal pulls. A separate, scoped local Cyber exception may authorize a policy-invalid historical release, with reason/use audit. Final authorization is checked again before serving cached/fetched content. Signature, publisher, digest and evidence failures remain denials.
5. **Deployment:** A separate database, portal/API and proxy run from `compose.replica.yaml`; the local registry is configured separately. The replica lifespan starts synchronization without assessment workers or blocking portal readiness. Existing service views consume imported evidence; release context preserves original source identity while local mapping controls access.

## Deployment readiness and limits

**Ready for local testing and a controlled staging qualification.** The implementation has evidence for complete publication/reconstruction, independent local enforcement, atomic reconciliation, scoped exceptions and a worker-free replica. This is not blanket certification of an arbitrary production Harbor or infrastructure configuration.

Before production, configure independent signer fingerprints, TLS ingress and custom CA trust, read-only target robot credentials, exact release repositories, namespace mappings, UTC clock synchronization, service-group mapping and named Local Cyber roles. Set unique database/bootstrap secrets and `CATS_CONFIG_ENCRYPTION_KEY`, preserve encrypted registry configuration, and back up the database together with retained evidence. Use secure sessions and OIDC as appropriate. The shipped replica compose binds locally and expects a TLS front end; do not disable verification to expose it.

Qualify the actual Harbor versions/adapter/filter with the full subtree, source-off pulls and recovery; measure capacity with the intended image count/size and sync interval. Verify monitoring, storage capacity, key rotation/revocation procedures and recovery from a consistent database/evidence backup. Production-scale performance, multi-host high availability, other registry versions, ARM execution and newly generated upstream revocations during total disconnection remain outside the demonstrated evidence. No implementation blocker is knowingly deferred to make a test pass.
