# Managed validator implementation and acceptance report

This report covers the requested 68 topics. The implementation is ready for review and automated testing; clean-VM acceptance remains unverified. A production installation payload has **not** been assembled or qualified in this development environment. A verified payload is a prerequisite, and HQ deliberately blocks provisioning without it. See [payload preparation](managed-validator-payload.md) and [architecture](managed-validator-architecture.md).

1. **Branch created.** Work is on `feature/hq-managed-validator-provisioning`. Existing dirty work was preserved. No commit or push was performed.
2. **Existing architecture reused.** The existing HTTPS/mTLS validator client, FastAPI worker, persisted validation jobs, v2 artifact transport, Kind/Helm engine, result schemas, remediation/bundle paths, encrypted settings, authorization and audit infrastructure remain authoritative. The manual validator setting remains supported.
3. **Overall architecture.** HQ manages durable validator records and asynchronous attempts. Pinned temporary SSH performs preflight, transfer, installation and enrollment. Normal validation, health, self-test and rotation use the existing mTLS API. Two bounded HQ provisioning workers execute jobs.
4. **Supported V1 operating systems.** Ubuntu Server 22.04 LTS and 24.04 LTS with systemd and cgroup v2; amd64 and arm64 require separate matching payloads. Unknown distributions and mismatched architectures fail preflight. Other platforms are deferred.
5. **Add Validator workflow.** Settings > Integrations > Managed validators > Manage Validators opens `/admin/validators`. Add a name, host/IP, SSH port (22), bootstrap username and API port (8443). Credentials are supplied later, after independent host-key confirmation, in password or private-key mode; an optional sudo password is available.
6. **Test Connection behavior.** Fingerprint discovery precedes authentication. After trust confirmation, Test Connection authenticates and returns host preflight without installing software. Credentials clear after submission and must be entered again to provision.
7. **SSH host-key trust behavior.** SHA256 host fingerprints are discovered without login, compared by the administrator against a trusted console, and explicitly pinned. Authentication rejects a changed or mismatched key. There is no silent trust-on-first-use or automatic replacement.
8. **Bootstrap credential handling.** Submission is ephemeral in the browser. Asynchronous bootstrap attempts persist only Fernet-encrypted credentials using the existing durable `CATS_CONFIG_ENCRYPTION_KEY`; responses and audit metadata omit secrets. Every success/failure clears the active encrypted credential field and in-memory credential mappings. The VM bootstrap account/password itself is not automatically deleted or changed.
9. **Preflight checks.** OS/version, architecture, CPU, memory, available disk, root/sudo authentication, systemd, cgroup v2, API-port availability, existing service, Docker facts and clock skew under five minutes are checked. Results are supported, supported with warnings, or unsupported. Firewall preservation is an explicit warning.
10. **Resource requirements.** Hard defaults: 2 CPUs, 4 GiB RAM and 20 GiB free space on `/var`. Recommended: 4 CPUs, 8 GiB RAM and 40 GiB free disk. Resource recommendations produce acknowledgement-required warnings; hard failures block provisioning. Workload needs may exceed these values.
11. **Provisioning payload architecture.** A versioned `manifest.json` declares platform, versions, file sizes/hashes, Kind/kubectl/Helm, validator application plus offline wheels, complete `.deb` package closure, digest-pinned node/test image archives and a local self-test chart. The builder packages already acquired local assets; it does not download or prove dependency closure.
12. **Disconnected installation behavior.** Installation uses `apt-get --no-download`, offline venv/pip wheels, local binary copies and local Docker archive loads. No repository update, pip index, registry pull or installer download is performed. Missing dependencies fail rather than falling back online.
13. **Payload integrity verification.** HQ requires an externally configured trusted manifest SHA256. Every file has checked size/SHA256; referenced assets must be declared; extra files, unsafe paths and symlinks are rejected. Remote installation rechecks transferred files. Archive extraction rejects links/devices and uses safe extraction. Hash integrity depends on trusted release preparation; it does not authenticate a publisher by itself.
14. **Remote workspace/layout.** Bootstrap uses a unique private `/tmp/cats-bootstrap-<uuid>` workspace. Application/venv: `/opt/cats-validator/app` and `/opt/cats-validator/venv`; identity/configuration: `/etc/cats-validator`; durable state/scratch: `/var/lib/cats-validator` and its `tmp`; local test assets: `/opt/cats-validator/self-test`. Workspace cleanup must complete before READY.
15. **Container runtime installation/reuse.** Docker Engine 28+ is installed from payload packages when absent; matching existing runtime installations are reused. Older Docker blocks with an explicit administrator upgrade requirement. Package incompatibility, daemon startup failure or failed `docker info` blocks success.
16. **Kind installation/configuration.** The payload Kind executable is installed locally. A digest-pinned local node image is configured. Kind creates an ephemeral cluster through the existing engine and deletes it during cleanup; successful service startup alone does not qualify the host.
17. **Helm/kubectl/tool installation.** Architecture-specific verified payload executables are copied to `/usr/local/bin`. Explicit versions are recorded in the manifest. Host provisioning has no tool-download fallback.
18. **Validator service installation.** `cats-validator.service` runs the existing validator server through the offline venv. It depends on Docker, uses `/etc/cats-validator/runtime.env`, restarts on failure, has private temporary storage, restrictive umask, `NoNewPrivileges` and a read-only system with writable validator state.
19. **Firewall/network behavior.** Existing firewall rules are preserved. HQ reports that the administrator must permit SSH and the chosen API port. The installer neither flushes host rules nor pretends to configure arbitrary firewalls. Network reachability is a manual prerequisite.
20. **Validator OS account/permissions.** A dedicated system account `cats-validator` has a non-login shell, private state/identity directories and Docker group membership. The application is readable and immutable to this account. Docker control remains powerful; the validator belongs on an isolated VM without production workloads.
21. **Validator CA/trust-domain implementation.** HQ persists a dedicated RSA-3072 validator CA and shared HQ client identity. Private CA/client keys use existing encrypted-secret storage. CA creation is serialized across database workers. The CA is valid for ten years and the initial HQ client identity for one year; automatic CA/client rollover is not implemented.
22. **Validator private-key generation.** Bootstrap generates the RSA-3072 server private key on the VM with mode 0600 and service ownership. HQ never receives it. Existing bootstrap keys can be reused for repair; operational rotation generates a new worker-local key.
23. **CSR enrollment flow.** An active authorized attempt, matching host-key pin, valid CSR signature, approved key strength, exact subject/SAN and restricted extensions are required. HQ signs the CSR, installs public certificate/CA and pins the authorized HQ client leaf fingerprint on the worker.
24. **Certificate identity.** Subject CN is the immutable managed-validator ID. SAN contains the configured DNS/IP plus `urn:cats:validator:<id>`. Certificates use server-auth EKU and expire within 90 days, bounded by CA expiry. HQ records serial, fingerprint, issue/expiry times, host, trust-domain ID and certificate history.
25. **mTLS transition.** HQ creates the same operational configuration shape as the manual endpoint, adding expected worker ID/server leaf fingerprint. It verifies HTTPS, identity, protocol and runtime capabilities through mTLS. Subsequent validation traffic needs no SSH.
26. **Bootstrap credential retirement.** Successful SSH workspace cleanup and encrypted credential removal are recorded stages before READY. Failures also clear HQ credentials. Remove or rotate temporary credentials on the VM after successful acceptance if local policy requires it; HQ retirement does not disable the account.
27. **Self-test implementation.** The operational API invokes the existing Kind engine with a local verified chart/image, strict sandbox policy, no network egress and local images required. It requires actual Helm install/release readiness, not manifest-apply emulation, plus complete cleanup. Cancellation is tracked.
28. **Local self-test artifacts.** The payload installs a minimal local Helm chart and workload image archive. A local SHA256 manifest protects test files. The node/test image references must be digest-pinned and inspectable after archive loading. The repository supplies the framework, not qualified third-party production binaries/images.
29. **READY criteria.** Valid enrollment and pinned mTLS health/identity/protocol; Docker/Kind/Helm/kubectl readiness; complete isolated Kind/Helm workload self-test; no external image/chart fetches; cleanup COMPLETE; retired HQ bootstrap credentials. A failed or unverified cleanup blocks eligibility.
30. **Validator states.** Records use DRAFT, PROVISIONING, SELF_TESTING, ROTATING, READY, DEGRADED, FAILED and REMOVED. Attempts use QUEUED, RUNNING, SUCCEEDED, FAILED and CANCELLED with retained stage history. Upgrade/re-enrollment share grouped bootstrap stages rather than separate per-package progress bars.
31. **Health monitoring.** HQ maintenance checks the mTLS API and updates last seen/health; failed checks degrade the record; health alone cannot restore a validator after a failed self-test. Scheduling requires recently checked health (within 120 seconds), active certificate with over five minutes validity, READY/enabled, advertised support for the requested validation type, available advertised job capacity and a verified last self-test. Maintenance does not recover retired SSH secrets.
32. **Test action.** Runs operational mTLS identity/protocol/runtime health checks and records an attempt. It does not require bootstrap credentials or create a Kind cluster.
33. **Self-Test action.** Runs the complete local Kind/Helm test over mTLS and retains results/cleanup. It clears active UI progress when terminal. Failure makes the validator ineligible until recovery succeeds.
34. **Certificate rotation.** Runs over authenticated mTLS: worker-local CSR/key creation, authorized HQ signing, certificate installation and health/self-test verification. HQ pins the new leaf and retains certificate metadata history. This is explicit administrator rotation; automatic expiry-driven rotation is deferred.
35. **Re-enrollment/recovery.** Supply fresh credentials against the confirmed SSH pin, repeat compatible preflight and the verified bootstrap path. Repair is an alias of provisioning. Lost server identity can be recovered this way. Wrong credentials, unsupported OS, host-key change and transfer/install/startup/enrollment/mTLS/self-test/cleanup errors retain safe failing-stage diagnostics; inspect the VM, correct the cause and explicitly retry. Changed host keys require independent investigation before trust is updated.
36. **Upgrade behavior.** Requires fresh bootstrap credentials, preflight, verified replacement payload and explicit UI confirmation and `confirm_upgrade: true` in the API request. It stops/replaces the application, re-enrolls and rechecks health/self-test. No automatic rollback or zero-downtime guarantee is implemented; failure may leave the host requiring repair.
37. **Removal/revocation behavior.** Explicit removal confirmation is required. HQ disables the record, clears operational configuration, marks certificate metadata revoked and excludes it from scheduling. Remote software is retained. The shared CA remains trusted by sibling validators; there is no CRL/OCSP enforcement, and removal does not revoke the shared HQ client identity or remotely uninstall the worker.
38. **Multiple-validator support.** Multiple managed records and independent attempts/certificates are supported. Scheduling selects the first eligible record ordered by recent last seen, then falls back to the existing manual configuration. It filters advertised validation types and full job capacity; load balancing and label routing remain deferred.
39. **Capability negotiation.** Enrollment/health requires Docker, Kind, Helm and kubectl capability flags plus the expected worker ID. Scheduling also checks advertised validation types and rejects workers at their advertised job limit. Broader resource/label matching is deferred.
40. **Protocol compatibility.** The existing v1 job/control and v2 artifact protocol is extended, not replaced. Managed health requires `cats.validation/v2`. Existing validation schemas and manual endpoints remain supported through the current transport paths.
41. **Authorization/permissions.** Separate global `validator.view`, `create`, `provision`, `test`, `self_test`, `rotate_certificate`, `upgrade` and `remove` permissions protect corresponding server routes. JSON mutations require CSRF; UI actions reflect permissions. Existing administrative account/authentication rules remain in force.
42. **Audit logging.** Creation, host-key discovery/trust, connection tests, requested/succeeded/failed operations, interrupted workers and removal are recorded through existing AuditEvent infrastructure. Safe identity/attempt/status metadata is retained; passwords/private keys/raw SSH outputs are excluded.
43. **Secret protection.** Browser fields reset before awaiting requests; credentials remain only in the temporary request closure after form clearing; they never enter React state, browser storage or page bootstrap DTOs. Persistent secrets use existing Fernet encryption. HQ CA/client and VM server keys have separate custody. Error evidence is deliberately sanitized; memory cannot be guaranteed physically zeroized by Python/JavaScript.
44. **SSRF/network safety.** Host/port/user syntax is validated; loopback, link-local, multicast and unspecified destinations are rejected, including resolved SSH addresses. Private LAN targets are intentionally permitted for administrators. Operational HTTPS validation remains in the existing client. This is not a network allowlist or defense against every DNS/network reconfiguration; deployment boundaries still matter.
45. **Remote-command safety.** Only checked-in bootstrap programs are invoked; inputs are validated and passed through private files/stdin rather than interpolated arbitrary install commands. Paths use controlled workspaces and safe quoting. Scripts propagate failures with `set -eu`; stdout/error content is bounded/sanitized. Provisioning payloads are privileged trusted executable code.
46. **Retry/idempotency behavior.** A database partial unique index allows one QUEUED/RUNNING attempt per validator. Worker claims are atomic and stage leases are refreshed to 40 minutes. Expired attempts fail and discard credentials; explicit retries need fresh credentials. Provision/repair tolerates existing accounts/runtime/service but is not transactional rollback. Cancellation and failed cleanup require inspection before retry.
47. **Provisioning history.** Durable attempts retain operator, action, payload digest, SSH fingerprint, timestamps, stage/status/detail, safe failure and cancellation metadata. The UI shows the latest 30 attempts. Progress groups runtime/account/service installation in one stage.
48. **UI changes.** Managed inventory/details, Add Validator, explicit fingerprint trust, auth-mode switching, preflight/warning gate, payload availability gate, progress polling, safe diagnostics/retry, operational Test/Self-Test/Rotate, Repair/Re-enroll/Upgrade and confirmed Remove. Manual Deployment Validation Sandbox settings remain accessible.
49. **Backend/API changes.** `/api/admin/validators` inventory/create, detail, connection, trust and action routes; `/admin/validators` HTML/page DTO; asynchronous management/maintenance; operational self-test and certificate endpoints extend the existing validator API. Existing deployment/remediation callers can select eligible managed configuration.
50. **Database/schema changes.** Additive `managed_validators`, `validator_provisioning_attempts` and `validator_trust_domains` tables hold identity/state/configuration, encrypted attempt credentials, histories, leases and encrypted CA/client keys. Existing manual PortalSetting configuration remains intact.
51. **Migrations.** Uses the repository's serialized SQLAlchemy `Base.metadata.create_all` additive schema mechanism, not a second migration framework. The active-attempt partial unique index targets PostgreSQL and SQLite. No destructive migration is introduced.
52. **Files added.** Feature files: `portal/app/validator_management.py`, `validator_bootstrap.py`, `validator_payload.py`, `validator_enrollment.py`, `validator_operations.py`, `validator_bootstrap_assets/*.sh`; `portal/frontend/src/features/validators.tsx` and its test; managed bootstrap/management/operations tests; `scripts/build-managed-validator-payload.py`; managed architecture, payload and this report documentation. Other already untracked work is preserved and must not be attributed wholesale to this feature.

57. **Security limitations.** Dedicated worker controls Docker; isolation is best effort on a dedicated VM. Administrators authorize private-network SSH and privileged payload execution. Shared HQ client/CA lack per-worker CRL/OCSP revocation. No automatic trust-domain rollover or guaranteed memory zeroization. Production payload provenance and network policy require release/deployment qualification.
58. **Current implementation limitations.** No real VM tested; no production payload built; offline dependency closure and digest-preserving image archives remain unqualified. Grouped progress, two HQ workers, 10-minute queued-attempt expiry and 40-minute running worker lease, first-eligible scheduling, manual firewall rules, explicit recovery and no upgrade rollback. Readiness/health UI uses structured details rather than a complete live capacity dashboard.
59. **Features intentionally deferred.** Additional distributions, automated asset acquisition/release qualification, automatic CA/client rollover, CRL/OCSP, autoscaling/load balancing/label routing, automated host firewall changes, remote uninstall, transactional upgrade rollback and automatic restart recovery with expired bootstrap credentials.
60. **Internet dependencies.** No public Internet access is required by the intended VM installation/self-test path when a qualified complete payload is supplied. A connected trusted staging environment normally acquires upstream OS packages/wheels/tools/images before release. Missing packages never silently download. Ordinary `docker save/load` can lose digest metadata: such archives fail the pinned identity check and are not accepted as a working disconnected release.
61. **Required network flows.** HQ -> VM TCP/22 (or configured SSH port) during bootstrap/recovery/upgrade. HQ -> validator TCP/8443 (or configured API port) for mTLS operation. Validator -> local Docker socket and ephemeral Kind control plane/container network. Additional trusted OCI/Helm endpoints are permitted only when required by the specific online validation; disconnected self-test/offline validation must make none. The worker does not call back to HQ for enrollment.
62. **Fresh Ubuntu manual prerequisites.** Install Ubuntu Server 22.04 LTS for the first acceptance test (24.04 LTS is also supported) on an isolated matching-architecture VM, ideally 4 vCPUs/8 GiB RAM/40 GiB free disk. Configure networking/time synchronization. Enable OpenSSH server during installation (or from trusted installation media), create a bootstrap user and give it usable root/sudo access. Ensure base `python3` is available for preflight and supplied sudo authentication works. Permit HQ's address to reach SSH and the configured API port without exposing it generally. Obtain IP/hostname and the SSH host-key SHA256 through the VM console (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`; compare the actually negotiated host key). Do not manually install Docker, Kind, Helm, kubectl or the validator on the target.
63. **First real managed provisioning test.** First prepare/qualify a Ubuntu 22.04 release payload using the separate payload guide. A multi-platform catalog can also include independently qualified 24.04 releases. On the HQ host set `CATS_VALIDATOR_PAYLOAD_HOST_DIR` to its absolute directory and `CATS_VALIDATOR_PAYLOAD_SHA256` to the independently retained manifest SHA256 (or catalog SHA256 when using a catalog); canonical Compose mounts it read-only at `/opt/cats/validator/payload` and passes `CATS_VALIDATOR_PAYLOAD_DIR` internally. For a different deployment explicitly mount that same directory/read-only and set both container environment values. Preserve the existing durable encryption key and database. Rebuild/redeploy HQ, sign in with validator permissions, open Manage Validators, verify Installation payload Available, Add Validator, Discover SSH fingerprint, independently compare and Confirm, enter credentials/Test Connection, review/acknowledge warnings, re-enter credentials and Provision Validator. Watch all terminal stages, wait for READY, then run Self-Test. Inspect VM service state and absence of remaining test clusters/workloads. Record manifest digest and attempt evidence; do not classify service startup as acceptance.
64. **Disconnected proof test.** Use a second fresh baseline VM or reset the first; remove public Internet routing/access while retaining HQ SSH/API reachability and any explicitly necessary local time service. Enforce this at the network boundary, not merely DNS. Provision from the mounted HQ payload without external package mirrors or registries. Require READY and a separately requested successful self-test. Confirm Docker loads pinned local node/test images, Kind starts, local image loads, local Helm release reaches readiness, and cleanup finishes. Inspect boundary logs for no public egress and retain zero external-image-pull/chart-fetch evidence. Unmet package dependencies or digest identity lost after archive load are release failures to repair on staging, not reasons to enable target Internet.
65. **Submit a real Helm chart.** With the managed validator READY, use the existing persistent service Helm ingestion workflow: choose/create a service, ingest a local packaged chart and required local image archives or explicitly configured trusted image sources, then complete scanning so its retained Helm artifact/values are available. Open that service's Deployment Validation tab and choose Re-run Validation using an account with the existing validation/remediation execution permission. Eligible managed configuration is selected automatically. Check the immutable validation run's artifact provenance, Helm/resource evidence and cleanup. For a disconnected test use only locally retained chart dependencies and images; remote URLs/registries invalidate the proof. The existing service validation path retains its strict sandbox semantics; full Helm lifecycle is explicitly exercised by managed self-test.
66. **Expected successful provisioning UI.** Inventory/details show READY; the terminal attempt shows SUCCEEDED and completed stages through MTLS API HEALTH, KIND HELM SELF TEST, BOOTSTRAP WORKSPACE CLEANUP and BOOTSTRAP SECRET RETIREMENT. Health is ready, last seen updates, last self-test is verified with cleanup COMPLETE, certificate metadata is active.
